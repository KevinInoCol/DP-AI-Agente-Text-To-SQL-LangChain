Arquitectura del agente Text-to-SQL CitiBike

DataBot responde preguntas en lenguaje natural sobre los viajes de CitiBike NYC: escribe el SQL, lo valida, lo ejecuta en BigQuery, delega los gráficos en un subagente y recuerda la conversación en PostgreSQL.

  • LangChain 1.x · create_agent
  • LangGraph · PostgresSaver
  • OpenAI gpt-4.1
  • BigQuery · sqlglot
  • FastAPI · Streamlit
  • Cloud Run
  • Supabase

    Capas

    Cada capa conoce solo la API pública de la siguiente. El Frontend nunca importa código del Backend; app.py no sabe nada de LLMs ni prompts.

    Instancias

    Frontend/app.py · Backend/app.py
    • Streamlit: cliente delgado, genera el thread_id y pinta respuesta, tools y gráficos.
    • FastAPI: POST /chat y GET /health; valida variables de entorno al arrancar.
    • Sin debounce: cada mensaje es un turno.

    LLM orquestador

    agent.py · estado.py
    • init_resources() crea una vez LLM, prompts, checkpointer, tools y subagente.
    • build_agent() se reconstruye por mensaje: barato, y el prompt depende del hueco desde el último mensaje.
    • Estado propio: EstadoAgente.

    Tools

    tools/bigquery.py · tools/graficos.py
    • consultar_bigquery(sql): valida y ejecuta; devuelve ≤ 50 filas al modelo.
    • generar_graficos(instruccion): subagente como tool; toma los datos del estado.

    Subagente de gráficos

    subagentes/graficos/
    • Decide (LLM, structured output → PlanGraficos), no dibuja.
    • Contexto aislado: solo un perfil de los datos, no la conversación.
    • El dibujo es código determinista (matplotlib): nunca inventa valores.

    Datos

    BigQuery/conexion.py
    • bigquery-public-data.new_york_citibike, de solo lectura.
    • Los jobs se facturan al proyecto de la Service Account.

    Histórico de conversación

    chat_history/ · migraciones_SQL/
    • Checkpoints de LangGraph: estado completo por thread_id.
    • chat_log: tabla plana para auditar con SQL.
    • PostgreSQL en Supabase (pooler).

    Cuatro barreras para el SQL del modelo

    El SQL que escribe un LLM no es de confianza. tools/bigquery.py lo trata como entrada externa.

    1. Validación con sqlglot (dialecto BigQuery)Una sola sentencia, solo consultas (SELECT / WITH / UNION) y solo tablas de TABLAS_PERMITIDAS dentro del proyecto y dataset permitidos.
    2. Tope de bytes facturadosmaximum_bytes_billed = 2 GB por consulta: BigQuery rechaza el job antes de ejecutarlo y el agente recibe una pista para reformular.
    3. Límite de filasEl modelo ve como máximo 50 filas; el estado guarda hasta 500 para graficar.
    4. Permisos mínimosLa Service Account solo tiene BigQuery Job User y el dataset es público y de solo lectura: aunque la barrera 1 fallara, no hay nada que escribir.

    Los datos viajan por el estado, no por el texto

    consultar_bigquery devuelve un Command(update=…) que guarda el resultado en ultima_consulta. generar_graficos lo lee de runtime.state: el LLM nunca copia números, así que no puede alterarlos.

    Como el estado se guarda en el checkpointer, “grafícalo” funciona también en el turno siguiente. graficos_turno se reinicia en cada invocación y app.py lo entrega como PNG en base64.

    Memoria

    Tres middleware, en este orden: resumir antes de descartar gastaría una llamada al LLM en mensajes que están por borrarse. Valores de model_config/model.yaml.

    ① Retención

    30 días

    descartar_vencidos corta en el primer mensaje humano vigente (sin ToolMessages huérfanos) y conserva el resumen. Lo descartado sigue en chat_log.

    ② Resumen

    3 000 tokens

    SummarizationMiddleware resume al superar el umbral y conserva los últimos 20 mensajes.

    ③ Prompt del turno

    6 horas

    dynamic_prompt inyecta fecha y hora (America/Lima) y, si el usuario vuelve tras 6 h, el bloque de retoma. Es transitorio: no se guarda en el historial.
